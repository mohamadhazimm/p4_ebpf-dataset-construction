# Sliver C2 testbed — labeled command-phase telemetry (plan)

Drafted 2026-11-13. No VM step has run. Every VM phase below needs its own explicit approval, as with every
other collection in this workspace.

## Why

The sinkhole C2 run (`sinkhole-c2-5min/20261113T084625506148Z`) captured real implants during their **check-in and
retry phase** only: their command-and-control servers are unreachable, so no sample ever reached a **command
phase** (no tasks, no results, no file transfers). The advisor asked for telemetry with C2 present in the
isolated lab.

This testbed supplies the missing command phase with **both ends ours**: our own Sliver server and our own
Sliver implants, inside the sealed internal network. It is adversary-emulation for detector training, the same
way CALDERA or Atomic Red Team generate labeled attacker telemetry; it is not the real downloaded malware under
command, and it never leaves the lab.

Controlled contrast it enables:

- **Same family, server down vs up.** The sinkhole run holds 8 real Sliver samples beaconing to dead servers.
  This run holds our Sliver implants beaconing to a live server that answers and tasks them. Same host + network
  sensors, same 5-minute protocol.
- **Beacon-only vs command phase.** Does an active session (command + response traffic) separate from a benign
  client that merely polls, where the beacon-only implants did not (interim: network features ~chance, host best
  at 20 s)?

## What stays true (safety boundaries)

- Guest `intnet=malnet` only; Sink `intnet=malnet` only. No NAT, bridged or host-only. Re-checked each phase.
- The Sliver server listens only on `10.0.0.1` (malnet). Its operator gRPC is bound to localhost on the Sink.
- No internet at any point. No downloaded malware sample is used as an implant or tasked.
- Implants are generated by us and only ever contact `10.0.0.1`.
- The operator script issues only a **fixed, benign** command list (below). It has no path to issue anything
  else; the list is hard-coded.
- Original TLS/off snapshot restored after every mutating phase. A new dataset variant; never merged with the
  paper dataset or the sinkhole run.

## Components

- `vendor/` — Sliver v1.7.9 `sliver-server_linux-amd64` and `sliver-client_linux-amd64` with their `.minisig`
  signatures. Host-side download; SHA-256 and verification recorded in `vendor/VERIFY.md`. Git-ignored (binaries).
- **Sink (REMnux, 10.0.0.1):** the Sliver server runs as a daemon for the whole collection (like INetSim did).
  It bundles its own cross-compilers, so it generates Linux implants self-contained — no Go toolchain needed on
  the Sink or here.
- **Guest (Ubuntu, 10.0.0.10):** each implant runs once, 300 s, under the `.22` collector, from the quiet
  baseline — identical settings to the sinkhole run.
- **Operator automation (Sink, localhost):** a version-matched `sliver-client` (or `sliver-py`) driven by a
  script that waits for the case's implant to check in and runs the fixed task list, logging each task, its
  response size and timing. These logs are records only; the detector features stay payload-free.

## Implant set (our own)

Transports mirror the Sliver samples we hold and Sliver's own options: **mTLS, HTTPS, WireGuard, DNS**. Each as a
short-interval **beacon** (so several check-ins and tasks fit in 300 s); mTLS and WireGuard also as interactive
**sessions**. All amd64 (our Sliver samples are amd64). Target `10.0.0.1`. Roughly:

| case | transport | mode | notes |
| --- | --- | --- | --- |
| mtls-beacon | mTLS :8443 | beacon 5 s | |
| mtls-session | mTLS :8443 | session | interactive |
| https-beacon | HTTPS :443 | beacon 5 s | |
| http-beacon | HTTP :80 | beacon 5 s | INetSim-style web answers come from our server |
| wg-beacon | WireGuard UDP | beacon 5 s | |
| wg-session | WireGuard UDP | session | interactive |
| dns-beacon | DNS | beacon 10 s | via the Sink's dnsmasq/our DNS listener |

Two or three independent builds per transport (different implant names/keys) so held-out grouping has something
to hold out. Final count fixed at freeze.

## Fixed benign task list (issued to each checked-in implant)

System information and small, in-lab file operations only:

1. `getuid` / `whoami`
2. `pwd`, `ls` of the working directory and a staged lab directory
3. read a staged lab text file (`cat`/download of a file we placed)
4. write a small file into the guest working directory (`upload`)
5. run a benign program (`execute id` / `uname -a`)
6. keep beaconing until the window ends

No scanning, no spreading, no persistence beyond the run, no privilege escalation, no exfiltration outside the
sealed network. The list is the same for every implant so the command phase is comparable.

## Benign controls and nulls

Reuse the sinkhole run's benign network clients (curl/wget/openssl/git/rsync/lowrate/whois) and the per-mode
nulls, so the benign side is identical and the only new thing is a live-C2 malicious side.

## Phases (each needs approval)

0. **Host prep (this).** Download + verify binaries, write and sandbox-test the harness. No VM.
1. **Sink setup.** Copy server + client to the Sink, start the server on malnet, generate all implants, copy the
   implants back. Sink VM only; no guest, no downloaded malware.
2. **Preflight.** Run each implant once in the guest under the collector; confirm check-in, that the task list
   runs, and that collector health is clean. Drop any implant that does not check in.
3. **Freeze** payload + interleaved order + protocol (hash-pinned), like the sinkhole run.
4. **Collect.** preflight / stage / dry-run / collect, with the operator script tasking each implant live during
   its window.
5. **Restore + analyse.** Stop the server, restore the Sink and guest, fetch server/operator logs, run the
   frozen analysis (`analyze_sinkhole_c2.py` + `conn_features.py`, same held-out protocol) plus the
   server-down-vs-up contrast. Report.

## Analysis

Same frozen detectors and protocol as the sinkhole run, so the two are directly comparable:

- host (ADFA-90), network (P4-145), connection features (30), their fusions, the stacked hybrid;
- malware families / benign programs held out, 10 fold assignments, 20 s / 1 min / 5 min;
- the server-down (sinkhole Sliver) vs server-up (this) contrast on the same sensors;
- per-run wire description (tasks issued, bytes each way, beacon cadence) for the write-up.

## Limits (stated up front)

- One framework (Sliver), so it is a **case study** of a live C2, not a broad result.
- Our implants are default builds, not tuned to evade; the host/network signatures are of a generic beacon doing
  benign lab tasks, which is the honest thing to measure for a detector.
- The command phase is a fixed benign script, not an operator improvising; it bounds, not matches, real tasking.
